# COP420

Microcontrolador de 4 bits que descarga al Z80 del teclado, el display
fluorescente, el cassette y parte del temporizado. Se comunica con el Z80 por
el puerto `06` (interfaz MICROBUS) y le interrumpe por `_COPINT`.

## Cableado (de MAME)

| Pata | Conexion |
|------|----------|
| IN0 | K8, salida Q2 del latch CD4076 (teclado) |
| IN1..IN3 | `_RD`, `_COP`, `_WR` del microbus |
| G0 (out) | `_COPINT` |
| G1, G3 (out) | `_TM1`, `_TM2` — motores de los dos cassettes |
| G1..G3 (in) | K9, K7, K3 del latch de teclado |
| D0 | invertido a K4 → reset del contador CD4024 |
| D1 | `TDO` — salida a cinta |
| D2 | invertido a K6 → reloj del CD4024 y del CD4076, y habilitacion del DS8881 |
| SO / SK | trama serie de 16 bits hacia el display fluorescente |
| SI | `TDI` = TPIN XOR TDO |

El teclado es una matriz de 16 filas × 4 bits: el contador CD4024 recorre las
filas y el latch CD4076 devuelve los cuatro bits.

El display son 16 digitos de 14 segmentos. El COP desplaza 16 bits por SO/SK
y el orden de los segmentos esta barajado; MAME lo desenreda con un
`bitswap<16>` cuyos indices son, de bit 15 a 0: 11, 7, 1, 13, 10, 3, 2, 12,
9, 5, 6, 4, 0, 8, 14, 15, quedandose con los 14 bits bajos.

## Protocolo de comandos

El emulador de cdesp no emula la CPU: implementa el protocolo. Comandos que
el Z80 escribe en el puerto `06`:

| Codigo | Nombre | Funcion |
|--------|--------|---------|
| `80` | CASSCOM | operacion de cassette |
| `8C` | CASSLOD | carga desde cassette |
| `90` | PASSCOM | paso de datos |
| `A0` | DISPCOM | escritura en el display |
| `B0` | TIMCOM | temporizador |
| `C0` | PDNCOM | apagado |
| `D0` | NULLCOM | nada |
| `F0` | RESCOM | reset |

Bits de estado que devuelve:

| Valor | Significado |
|-------|-------------|
| `00` | REGINT |
| `10` | CASSERR |
| `20` | CASSIN |
| `30` | KBD |
| `40` | CASSOUT |

## Secuencia de la interrupcion

Rutina `COPIS`, en `E225` de la ROM EF:

    E225  LD C,06
    E227  IN A,(C)        ; lee el vector de interrupcion
    E229  LD HL,COPCTL    ; 003B
    E22C  LD D,(HL)
    E22D  OUT (C),D       ; devuelve el byte de reconocimiento
    E22F  INC HL          ; HL -> COPSTATUS (003C)
    E230  LD B,10H
    E232  SUB B / JR C    ; encadenado, segun el nibble alto del vector

Ramas: `0X` REGINT, `1X` CASSERR, `2X` CASSIN, `3X` KBD, `4X` CASSOUT.

### REGINT (`E298`)

Copia los bits 0 a 2 del vector (TIMER0, BATTLOW, BRK, RESP) a `COPSTATUS`,
deja `NULLCOM` preparado como siguiente reconocimiento y, **segun cual fue
el byte de reconocimiento que acaba de enviar**, decide si toca enviar un
bloque:

| Reconocimiento previo | Bloque |
|-----------------------|--------|
| `A0` DISPCOM | 18 bytes desde `OUTBUFF` |
| `B0` TIMCOM | 6 bytes desde `TIMBUFF` |
| otro | nada |

Antes de enviarlo espera en `SYNDLP` (`E2BA`) a que `_COPINT` **y** `_CLKINT`
esten los dos pendientes. Por eso el HLE vuelve a bajar `_COPINT` justo
despues de recibir un reconocimiento DISPCOM o TIMCOM: si no, el Z80 se queda
girando en ese bucle.

### KBD (`E278`)

El Z80 lee del puerto `06` **dos veces**:

1. la primera tiene que devolver algo **distinto de `80`**, que es lo que le
   saca de su bucle de espera;
2. la segunda es la que lleva el codigo de tecla.

Entregar la tecla en la primera lectura no funciona, y ademas falla de forma
engañosa: el codigo se lo traga el centinela y lo que la ROM recibe como tecla
es el `80` siguiente, o sea "no hay tecla". Sobre hardware el sintoma es que
el cursor cambia de forma al pulsar cualquier tecla -- incluidas Espacio e
Intro -- pero no se escribe nada.

El valor del centinela que usa el emulador de cdesp es `85`, y es el que
usamos. En la fase 2 se descarto como si fuera un apaño de su emulador; era el
protocolo.

Despues la ROM guarda el byte y le aplica `AND 3FH`. Ver `03-teclado.md` para
el formato.

### CASSIN y CASSOUT: el protocolo completo

Desensamblado de la ROM v2.0 real, no de la version parcheada de cdesp.

**CASSOUT, vector `4X`.** El COP pide un byte para grabarlo:

    E240  CALL E26D        ; CASSVR: apaga el video
    E243  LD B,3Bh         ; CODEL = 59
    E245  DJNZ $           ; retardo calibrado
    E247  LD A,(HL)        ; HL apunta a COPSTATUS+1
    E248  OUT (C),A        ; se lo entrega al COP
    E24A  RET

**CASSIN, vector `2X`.** El COP tiene un byte leido de la cinta:

    E24B  RRA              ; bit 0 del vector
    E24C  JR C,+13         ; si esta puesto, es error de lectura
    E24E  CALL E26D        ; CASSVR
    E251  LD B,52h         ; CIDEL = 82
    E253  DJNZ $
    E255  IN A,(C)         ; recoge el byte
    E257  LD (HL),A        ; lo guarda
    E258  RET

Tres cosas que importan para implementarlo:

1. **Un byte por interrupcion**, no un bloque. Nada que ver con los 18 de
   DISPCOM.
2. **El bit 0 del vector de CASSIN no es un error de lectura**, como
   creiamos: marca que el vector es de estado y no trae dato. Si ademas
   esta el bit 1, es BREAK (`SCHBIT` en `OS.S2`). El error de lectura llega
   por el vector `1X` (`DROPOUTERR`).
3. **El retardo no es decorativo.** Entre el reconocimiento y el acceso al
   puerto hay 82 o 59 vueltas de `DJNZ`, y antes de eso se apaga el video
   escribiendo en `ENREG`. El apagado hace falta porque el robo de ciclos de
   DRAM del generador de imagen descuadraria el temporizado, y el retardo le
   da tiempo al COP a tener el dato listo. Un HLE que conteste
   instantaneamente probablemente funcione igual, pero conviene no
   adelantarse al retardo.

El encadenado de ramas en `E230` tambien queda confirmado:

| Vector | Rama | Direccion |
|--------|------|-----------|
| `0X` | REGINT | `E298` |
| `1X` | CASSERR | `E264` |
| `2X` | CASSIN | `E24B` |
| `3X` | KBD | `E278` |
| `4X` | CASSOUT | `E240` |
| `5X` y mas | se ignora | `RET` |

## Por que LOAD daba ERROR 131

ERROR 131 es `LENGTHERR`, no un tiempo agotado: la ROM ha leido una longitud
de bloque mayor que el buffer. La longitud le llegaba mal porque **el HLE
seguia mandando REGINT durante la carga**, y cualquier interrupcion pone el
bit READY que espera `TCHR`, que entonces devuelve basura en vez de un byte
de cinta.

Las reglas del protocolo de cassette, sacadas del fuente original `TPIO.S` y
`OS.S2`, estan en `doc/11-cinta.md`. En resumen:

1. Mientras se reproduce solo se generan vectores `2X`; mientras se graba,
   solo `4X`. Nada de REGINT ni de teclado en medio.
2. El comando `CASSCOM` llega **dos veces** por bloque, como reconocimiento
   de dos interrupciones seguidas. La segunda se ignora.
3. El primer byte de cada bloque (el `00` de sincronismo) lo lee `PRETRD` y
   lo tira: entra en `TCHR` por `RST 8` y vuelve a caer en ella.
4. Tras la suma de control se para, y la cola de nueve ceros no se entrega.
5. `NULLCOM` en el reconocimiento mientras se reproduce significa que la ROM
   ha abandonado el bloque.

Corregido esto, la carga funciona de punta a punta contra la ROM real; ver
`tools/nbcinta.py` y `make rom`.

## Plan

1. Stub — fase 1, nunca interrumpe. **Hecho y retirado.**
2. HLE del protocolo (`newbrain_cop_hle.v`) — **hecho**. REGINT periodico,
   teclado, bloques de DISPCOM y TIMCOM, y cassette completo en las dos
   direcciones, contrastado contra la ROM real.
3. Core COP400 en HDL con `cop420-guw.ic419`, validado comparando el trafico
   del puerto `06` contra el HLE.

Problemas conocidos en MAME que conviene no heredar: `COPINT` puede estar a
84 Hz y no a 50, `CLKINT` llega tarde y el COP lee el dato del display antes
de que la CPU lo escriba.
